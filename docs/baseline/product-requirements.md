## プロダクト概要

### 名称
**HabitOS** - 習慣継続を可視化するセルフマネジメント Web アプリ

### プロダクトコンセプト
- **繰り返しルールに忠実なチェックイン**: 「毎日／週N回／特定曜日」という現実的な習慣の形に合わせ、
  その日が対象の習慣だけを提示する。
- **継続を数字で見せる**: ストリーク（連続達成）と達成率、カレンダーヒートマップで、続いている実感と
  途切れた事実を等しく可視化する。
- **正しいドメインロジック**: 繰り返し判定・ストリーク計算・期間集計という非自明なロジックを、
  テストで裏づけられた形で正確に実装する。

### プロダクトビジョン
HabitOS は、日々の習慣を登録し、その日が対象の習慣にチェックインし、ストリークと達成率で継続を
可視化する Web アプリである。ユーザーは「今日やるべきこと」と「どれだけ続いているか」を一目で把握でき、
継続のモチベーションを保てる。本プロジェクトはこの実用アプリを題材に、ウォーターフォール型の開発
ワークフロー（要件定義→基本設計→詳細設計→テスト設計→実装→結合テスト）を欠落なく一通り回すことを
主目的とする。ドメインモデルが明確で非自明なロジックを持ち、フロント↔バックの連携があるため、設計・
テスト設計・結合テストの題材として適している。

### 目的
- **プロダクトとしての目的**: 習慣の登録・チェックイン・可視化を通じて、ユーザーの習慣継続を支援する。
- **プロジェクトとしての目的（主目的）**: ウォーターフォール型ワークフローを一通り実践し、設計・
  テスト設計・結合テストの一連の工程を成果物として残す。
- **実用性の兼備**: 開発者自身が日々使えるだけの実用性を持たせる。

## ターゲットユーザー

第一マイルストーンは**単一ユーザー前提**（認証・マルチユーザーなし）。開発者自身がプライマリー
ペルソナを兼ねる。

### プライマリーペルソナ: 開発者本人（自己管理したい個人ユーザー）
- **基本属性**: Web アプリ開発に習熟したエンジニア。自分の習慣（運動・学習・生活リズム等）を
  継続したいが、続いているかどうかの実感が持ちにくい。
- **技術環境**: PC ブラウザ中心。ローカル環境でアプリを起動して利用する。
- **現在の課題**:
  - 習慣が「毎日」だけでなく「週3回」「月・水・金」のような形を取るため、単純な連続日数では
    継続を正しく測れない。
  - 続いているのか途切れたのかが数字で見えず、モチベーションが続かない。
  - 過去の記録を後から修正したい（付け忘れ・後追い入力）。
- **期待する解決策**: その日が対象の習慣だけを提示してほしい。ストリークと達成率、ヒートマップで
  継続状況を一目で把握したい。過去日も遡って記録・修正したい。
- **1日の典型的なワークフロー**: 朝または就寝前にダッシュボードを開き、当日対象の習慣を確認して
  チェックインする。リマインド時刻を過ぎた未完了はハイライトで気づける。週次・月次で達成率と
  ヒートマップを振り返る。

## 成功指標(KPI)

本プロジェクトは学習・実践が主目的のため、KPI は「ワークフロー完遂」と「プロダクト品質」の両面で
測定する。

### プライマリーKPI（プロジェクト＝ワークフロー完遂）
- **工程完遂率**: 要件定義→基本設計→詳細設計→テスト設計→実装→結合テストの6工程を欠落なく完了
  （目標: 100%、第一マイルストーン完了時）。各工程の成果物（本 PRD・機能設計・アーキテクチャ・
  リポジトリ構造・テスト設計・実装・結合テスト）が残っていることで測定。
- **ドメインロジックのテストカバレッジ**: 繰り返し判定・ストリーク計算・期間集計のコアロジックで
  ステートメントカバレッジ 90% 以上（第一マイルストーン完了時、Go のカバレッジ計測で測定）。
- **結合テスト成功**: コアユースケース（登録→チェックイン→可視化）が E2E 結合テスト（Playwright、
  ブラウザ↔Go API）でグリーン（目標: 100% パス）。

### セカンダリーKPI（プロダクト品質）
- **主要 API 応答時間**: ダッシュボード表示に必要な集計 API が p95 で 300ms 以内（ローカル環境、
  習慣50件・チェックイン1年分規模のシードデータで測定）。
- **ストリーク/達成率の正当性**: 定義したエッジケース（対象外の日を跨ぐ継続／未完了での途切れ／
  週N回・特定曜日ルール）が全て仕様どおり（テストケース通過率 100%）。
- **実用性**: 開発者本人が第一マイルストーン完了後、日次チェックインを継続利用できる状態にある。

## 機能要件

### コア機能(MVP)

#### 1. 習慣の管理（CRUD）

**ユーザーストーリー**:
自己管理したいユーザーとして、自分の習慣を実態に合った繰り返しルールで管理するために、習慣を
登録・編集・削除できる機能が欲しい。

**受け入れ条件**:
- [ ] 名前・カテゴリ・繰り返しルール（毎日／週N回／特定曜日）を指定して習慣を登録でき、一覧に反映される
- [ ] 習慣を編集・削除でき、その結果が一覧とチェックイン対象に正しく反映される
- [ ] 習慣ごとに任意のリマインド時刻を設定・保持できる（実配信は行わない）
- [ ] 繰り返しルールのバリデーション（週N回の N が1〜7、特定曜日が1つ以上選択）がエラーとして機能する

**優先度**: P0(必須)

#### 2. 日次チェックイン

**ユーザーストーリー**:
自己管理したいユーザーとして、今日やるべき習慣だけに集中して記録するために、指定日付で対象の習慣に
完了／未完了を記録できる機能が欲しい。

**受け入れ条件**:
- [ ] 日付を指定すると、その日が繰り返しルール上の対象である習慣のみがチェックイン対象として表示される
      （週N回・特定曜日ルールでも正しく判定される）
- [ ] 各習慣を「完了／未完了」で記録でき、記録は即座に反映・永続化される
- [ ] 過去日を指定して遡り記録・修正ができ、その結果がストリーク・達成率に反映される
- [ ] 当日ダッシュボードで、リマインド時刻を過ぎた未完了の習慣がハイライト表示される
- [ ] 同一習慣・同一日付のチェックインは重複せず、最新状態が一意に保たれる

**優先度**: P0(必須)

#### 3. ストリーク・達成率の算出と可視化

**ユーザーストーリー**:
自己管理したいユーザーとして、継続できているかを一目で把握するために、ストリークと達成率、
カレンダーヒートマップを見られる機能が欲しい。

**受け入れ条件**:
- [ ] 習慣ごとに現在ストリーク・最長ストリークが算出される（繰り返しルールに従い、対象外の日は
      連続を途切れさせない／対象日の未完了で途切れる）
- [ ] チェックイン記録の追加・修正に応じてストリークが正しく再計算される
- [ ] 週次・月次の達成率（対象日に対する完了日の割合）が算出・表示される
- [ ] カレンダーヒートマップで、対象日／完了日／未完了日が視覚的に区別して表示される
- [ ] ダッシュボードに達成率・ストリーク・ヒートマップが集約表示される

**優先度**: P0(必須)

### 画面構成（Web UI の主要ビュー）

Next.js による Web UI。ブラウザから Go API（REST）を直接呼び出す。

- **ダッシュボード（当日）**: 当日対象の習慣一覧＋チェックイン、リマインド超過ハイライト、
  ストリーク・達成率サマリー、ヒートマップ。
- **習慣管理**: 習慣の一覧・登録・編集・削除フォーム。
- **チェックイン（日付指定）**: 任意日付を選び、対象習慣に完了／未完了を記録・修正。
- **習慣詳細**: 個別習慣のストリーク推移・達成率・ヒートマップ。

### 将来的な機能(Post-MVP)

#### リマインド通知の実配信
リマインド時刻に基づくメール／ブラウザプッシュ等のスケジューリング配信。第一マイルストーンでは
時刻の保持のみ。

**優先度**: P2(できれば)

#### 認証・マルチユーザー対応
ユーザー登録・ログインと、ユーザーごとのデータ分離。技術スタック（PostgreSQL）は将来の拡張を
見据えて選定済み。

**優先度**: P1(重要)

#### 目標連携・AI による習慣提案 / モバイル・オフライン対応
上位目標との紐付け、達成傾向に基づく習慣提案、モバイルアプリ／オフライン利用。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス
- ダッシュボードの集計 API（ストリーク・達成率・ヒートマップ）: p95 で 300ms 以内
  （ローカル環境、習慣50件・チェックイン1年分規模で測定）。
- チェックイン記録の書き込み〜画面反映: 200ms 以内（ローカル環境）。

### ユーザビリティ
- 当日ダッシュボードを開いて対象習慣をチェックインするまで、3クリック以内で完了できる。
- リマインド時刻を過ぎた未完了習慣が、他と視覚的に区別できる形でハイライトされる。

### 信頼性・データ整合性
- チェックイン記録はデータ損失なく永続化される（PostgreSQL、マイグレーションで管理）。
- 同一習慣・同一日付のチェックインは一意制約で重複しない。
- ストリーク・達成率は保存済みチェックインから決定論的に再計算でき、同じ入力に対し常に同じ結果を返す。

### 保守性・テスト容易性（本プロジェクトの主眼）
- ドメインロジック（繰り返し判定・ストリーク・集計）は外部依存なしに単体テスト可能な形で分離する。
- API 契約は OpenAPI（`openapi.yaml`）を正本とし、Go・TS 両方の型を生成して契約不一致を防ぐ。
- DB 結合テストは testcontainers-go で本物の PostgreSQL に対して実行する。
- コアユースケースは Playwright による E2E 結合テストで検証する。

### セキュリティ
- 第一マイルストーンは単一ユーザー・ローカル前提のため認証は持たない（スコープ外）。
- 入力値のバリデーション（繰り返しルール・日付・N の範囲）をサーバー側で行い、不正入力を拒否する。
- 将来の認証追加を見据え、データモデルにユーザー分離を後付けできる余地を残す（設計上の配慮）。

### スケーラビリティ
- 単一ユーザーの数年分のチェックイン規模（数千〜数万レコード）で集計が実用速度を保つ。
- 将来のマルチユーザー化に向け、PostgreSQL を採用しスキーマ拡張で対応できるようにする。

## スコープ外

第一マイルストーンでは以下を実装しない（後続マイルストーンへ）:
- リマインド通知の実配信（メール／ブラウザプッシュ等のスケジューリング基盤）
- 認証・マルチユーザー対応（第一マイルストーンは単一ユーザー前提）
- 目標連携、AI による習慣提案
- モバイルアプリ／オフライン対応

## 未決事項（詳細設計フェーズで確定）

以下は要件レベルでは確定せず、詳細設計で判断する（`docs/baseline/ideas/tech-stack.md` にも記載）:
- タイムゾーン・日付境界の扱い（サーバー時刻基準か／ユーザーTZか）
- 「特定曜日」ルールでのストリーク継続仕様の詳細（対象外の日をどう跨ぐか）
- リマインド時刻超過ハイライトの判定基準（当日のみ／サーバー時刻基準）
- 認証／通知実配信を後続マイルストーンで追加する際の区切り
