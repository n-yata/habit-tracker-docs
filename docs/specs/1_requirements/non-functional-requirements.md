## 1. はじめに

### 1.1 目的

本書は、HabitOS 第一マイルストーンが満たすべき非機能要件（性能・信頼性・セキュリティ・運用保守性・
ユーザビリティ等）を定義し、発注者・開発者間で合意することを目的とする。各要件は測定可能な目標と
測定方法を伴い、以降の設計・実装・テスト工程で検証される。

### 1.2 分類方針

本書は IPA「非機能要求グレード」の大分類を参考に、本プロジェクトに該当する観点を定義する。第一
マイルストーンは**単一ユーザー・ローカル環境前提**のため、可用性・移行性・システム環境の一部は
限定的または対象外となる。対象外の観点も「なぜ対象外か」を明示する（§8）。

| 大分類（IPA 非機能要求グレード相当） | 本書での扱い | 該当節 |
|---|---|---|
| 性能・拡張性 | 定義する | §3 |
| 信頼性・データ整合性（可用性含む） | 定義する | §4 |
| セキュリティ | 定義する | §5 |
| 運用・保守性・テスト容易性 | 定義する（本プロジェクトの主眼） | §6 |
| ユーザビリティ | 定義する | §7 |
| 移行性・システム環境 | 限定的／対象外を明示 | §8 |

### 1.3 要件一覧（サマリー）

| NFR-ID | 分類 | 要件 | 目標・基準 |
|---|---|---|---|
| NFR-01 | 性能 | ダッシュボード集計 API の応答時間 | p95 で 300ms 以内 |
| NFR-02 | 性能 | チェックイン記録の書き込み〜画面反映 | 200ms 以内 |

| NFR-07 | 信頼性 | 集計の決定論性 | 同じ入力に常に同じ結果 |

## 2. 前提条件

| # | 内容 |
|---|---|
| 1 | 第一マイルストーンは単一ユーザー・ローカル環境前提とする |
| 2 | 性能の測定は、習慣50件・チェックイン1年分規模のシードデータを用い、ローカル環境で行う |
| 3 | 日付・時刻はサーバーローカル時刻基準で扱う |

## 3. 性能・拡張性

### 3.1 応答性能

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-01 | ダッシュボードの集計 API（ストリーク・達成率・ヒートマップ）の応答時間 | p95 で 300ms 以内 | 習慣50件・チェックイン1年分規模のシードデータに対し、ローカル環境で集計 API を反復呼び出しし、応答時間の p95 を計測 |
| NFR-02 | チェックイン記録の書き込み〜画面反映 | 200ms 以内 | チェックイン記録 API の呼び出し〜UI 反映までの時間をローカル環境で計測 |

### 3.2 拡張性・スケーラビリティ

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-10 | 単一ユーザーの数年分（数千〜数万レコード）の集計が実用速度を保つ | NFR-01/NFR-02 の性能目標を、数千〜数万レコード規模でも満たす | シードデータ規模を拡大して NFR-01/NFR-02 を再計測 |
| NFR-11 | 将来のマルチユーザー化に対応できる | PostgreSQL 採用によりスキーマ拡張（ユーザー分離）で対応できる設計であること | 設計レビューでデータモデルにユーザー分離の後付け余地があることを確認 |

**設計上の配慮**:
- ダッシュボード集計は期間指定でチェックインを一括取得し、ドメイン層でメモリ集計する（N+1 回避）。
- 集計クエリは明示的に記述し、`(habit_id, date)` 等のインデックスを利用する。
- フロントエンドはキャッシュ＋楽観更新で体感速度を保つ。

## 4. 信頼性・データ整合性

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-05 | チェックイン記録がデータ損失なく永続化される | PostgreSQL に永続化され、マイグレーションでスキーマを管理する | 結合テスト（本物の PostgreSQL）で記録の永続化・再取得を検証 |
| NFR-06 | 同一習慣・同一日付のチェックインが重複しない | 一意制約（habit_id, date）で重複を防止する | 重複登録を試行し、一意制約で拒否／upsert で最新化されることを結合テストで検証 |
| NFR-07 | ストリーク・達成率が決定論的である | 保存済みチェックインから決定論的に再計算でき、同じ入力に常に同じ結果を返す | ドメインロジックの単体テストで、同一入力に対する結果の一意性を検証 |

**可用性について**: 第一マイルストーンは単一ユーザー・ローカル環境前提のため、冗長化・SLA 等の
可用性要件は定めない（§8 参照）。データ整合性は上記 NFR-05〜07 で担保する。

## 5. セキュリティ

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-08 | 入力値をサーバー側で検証し、不正入力を拒否する | 繰り返しルールの整合・N の範囲（1〜7）・日付形式・状態値をサーバー側で検証する | 異常系の入力（範囲外 N・不正な曜日・不正日付・非対象日への記録）に対し、適切なエラーで拒否されることをテストで検証 |
| NFR-09 | 認証 | 第一マイルストーンは単一ユーザー・ローカル前提のため認証は持たない。将来のユーザー分離を後付けできる設計余地を残す | スコープ外（§8）。設計レビューで拡張余地を確認 |

**セキュリティ上の配慮**:
- SQL はパラメータ化クエリを用い、文字列連結によるインジェクションを避ける。
- サーバー側バリデーションを正とし、クライアント側検証のみに依存しない。
- 認証は第一マイルストーンのスコープ外だが、データモデルにユーザー分離を後付けできる余地を残す。

## 6. 運用・保守性・テスト容易性

本プロジェクトの**主眼**。ドメインロジックの正確さをテストで裏づけることを最重要視する。

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-12 | ドメインロジックを外部依存なしに単体テスト可能な形で分離する | 繰り返し判定・ストリーク・集計を、DB・HTTP を知らない純粋なロジックとして分離する | 設計レビュー・単体テストで、ドメイン層が外部依存なしにテストできることを確認 |
| NFR-13 | API 契約を一元管理し、契約不一致を防ぐ | API 契約は OpenAPI を正本とし、サーバー（Go）・クライアント（TS）両方の型を生成する | 契約から生成した型で実装され、契約不一致がビルド／型検査で検出されることを確認 |
| NFR-14 | ドメインロジックのテストカバレッジ | 繰り返し判定・ストリーク・集計でステートメントカバレッジ 90% 以上 | カバレッジ計測ツールでドメインロジックのステートメントカバレッジを測定 |

**検証方針（参考）**: ドメインロジックは単体テスト、Repository・ユースケースは本物の PostgreSQL を
用いた結合テスト、コアユースケースは E2E テストで検証する。テスト戦略の詳細は
`docs/specs/_shared/cross-cutting.md`「テスト戦略」を参照する。

## 8. 対象外・限定対応の観点

第一マイルストーンのスコープに照らし、以下の非機能観点は対象外または限定対応とする。理由を明示する。

| 観点 | 扱い | 理由 |
|---|---|---|
| 可用性（冗長化・SLA・障害復旧） | 対象外 | 単一ユーザー・ローカル環境前提のため、稼働率保証や冗長構成は不要 |
| 移行性（既存データ移行） | 対象外 | 新規構築であり、移行元データが存在しない |
| システム環境・エコロジー（設置環境・省電力等） | 対象外 | ローカル開発環境での起動を前提とし、データセンター設置要件を持たない |
| 運用監視・バックアップ運用 | 限定対応 | 本格的な監視・定期バックアップ運用は定めない。データ永続化と整合性（§4）で最低限を担保 |
| 認証・アクセス制御 | スコープ外（拡張余地を残す） | 単一ユーザー前提（NFR-09）。将来のマルチユーザー化でユーザー分離を後付けできる設計とする |

> これらは後続マイルストーン（認証・マルチユーザー対応等）で必要に応じて要件化する。
