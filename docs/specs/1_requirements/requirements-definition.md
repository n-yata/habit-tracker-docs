## 1. はじめに

### 1.1 本書の目的

本書は、HabitOS 第一マイルストーンの開発にあたり、システムが満たすべき要件（機能要件・非機能要件）を
定義し、発注者・開発者間で合意することを目的とする。以降の基本設計以降の工程は、本書で合意した要件を
起点として進める。

### 1.2 背景

日々の習慣（運動・学習・生活リズム等）は「毎日」だけでなく「週3回」「月・水・金」のような繰り返しの形を
取るため、単純な連続日数では継続を正しく測れない。また、続いているのか途切れたのかが数字で見えず、
モチベーションが続かないという課題がある。本システムは、繰り返しルールに忠実なチェックインと、
ストリーク・達成率・カレンダーヒートマップによる可視化で、この課題の解決を図る。

### 1.3 本書の位置づけと関連文書

本書は要件定義工程の成果物である。要件の正本および関連する設計文書は以下を参照する。

| 文書 | 役割 |
|---|---|
| `docs/baseline/product-requirements.md` | プロダクト要求定義書（PRD）。プロダクトビジョン・KPI・要件の正本 |
| `docs/baseline/functional-design.md` | 機能設計書。データモデル・中核アルゴリズム・API/画面/ユースケース一覧の正本 |
| `docs/baseline/architecture.md` | アーキテクチャ設計書。システム構造・技術選定の正本 |
| `docs/baseline/glossary.md` | 用語集（ユビキタス言語）。本書で用いる用語の定義 |

### 1.4 用語

本書で用いる主要な用語は `docs/baseline/glossary.md`（用語集）を正本とする。特に重要な用語を再掲する。

| 用語 | 意味 |
|---|---|
| 習慣（Habit） | ユーザーが継続したい行動。繰り返しルールを持つ |
| 繰り返しルール（RecurrenceType） | 習慣の対象日を定めるルール。`daily`（毎日）／`weekly_count`（週N回）／`specific_days`（特定曜日） |
| チェックイン（CheckIn） | ある習慣・ある日付に対する完了／未完了の記録 |
| 対象日 | 繰り返しルール上、その習慣を実施すべき日 |
| ストリーク（Streak） | 対象日の連続達成数。現在ストリークと最長ストリークを持つ |
| 達成率 | 期間内の対象日に対する完了日の割合 |
| ヒートマップ | 各日の達成状況（完了／未達成／未記録／非対象）を色分けしたカレンダー表示 |

## 2. システム概要

### 2.1 プロダクトコンセプト

HabitOS は、日々の習慣を登録し、その日が対象の習慣にチェックインし、ストリークと達成率で継続を
可視化する Web アプリケーションである。以下の3点を柱とする。

- **繰り返しルールに忠実なチェックイン**: 「毎日／週N回／特定曜日」に合わせ、その日が対象の習慣だけを提示する。
- **継続を数字で見せる**: ストリーク・達成率・カレンダーヒートマップで、続いている実感と途切れた事実を等しく可視化する。
- **正しいドメインロジック**: 繰り返し判定・ストリーク計算・期間集計という非自明なロジックを、テストで裏づけられた形で正確に実装する。

### 2.2 対象利用者

第一マイルストーンは**単一ユーザー前提**（認証・マルチユーザーなし）とする。

| 利用者 | 説明 |
|---|---|
| 自己管理したい個人ユーザー | 自分の習慣を継続したい個人。PC ブラウザから、ローカル環境で起動したアプリを利用する。習慣が「週3回」「特定曜日」の形を取るため、正しい継続の可視化と、過去日の遡り記録・修正を必要とする |

### 2.3 システム構成の概要

ブラウザ（Next.js が配信する UI）から Go 製 API（REST）を直接呼び出し、API が PostgreSQL を読み書きする
構成とする。詳細な構成・技術選定は `docs/baseline/architecture.md`、`docs/baseline/functional-design.md`
「システム構成図」を正本とする。

| 層 | 技術 | 役割 |
|---|---|---|
| フロントエンド | Next.js（React + TypeScript） | UI レンダリング。ブラウザから REST API を呼ぶ |
| バックエンド | Go（chi / OpenAPI / sqlc） | REST API。ドメインロジック（繰り返し判定・ストリーク・集計）を担う |
| データストア | PostgreSQL | 習慣・チェックイン記録の永続化 |

## 3. 利用シナリオ

代表的な利用の流れを示す（詳細なユースケース定義は基本設計工程・`functional-design.md`
「ユースケース一覧」に引き継ぐ）。

### 3.1 習慣を登録する

ユーザーは習慣管理画面で、習慣名・カテゴリ・繰り返しルール（毎日／週N回／特定曜日）・任意のリマインド
時刻を指定して習慣を登録する。登録した習慣は一覧に反映され、以後チェックインの対象となる。

### 3.2 当日の習慣にチェックインする

ユーザーは朝または就寝前にダッシュボードを開く。その日が対象の習慣だけが提示され、各習慣を完了／未完了で
記録する。リマインド時刻を過ぎた未完了の習慣はハイライトで気づける。

### 3.3 過去日を遡って記録・修正する

付け忘れや後追い入力のため、ユーザーは日付を指定して過去日の対象習慣に完了／未完了を記録・修正する。
記録の修正はストリーク・達成率に正しく反映される。

### 3.4 継続状況を振り返る

ユーザーはダッシュボードや習慣詳細で、現在ストリーク・最長ストリーク・週次/月次の達成率・カレンダー
ヒートマップを確認し、継続状況を振り返る。

### 4.1 機能一覧

| FR-08 | 完了／未完了の記録 | 対象習慣に完了／未完了を記録し、即座に反映・永続化する | P0 |
| FR-09 | 過去日の遡り記録・修正 | 過去日を指定して記録・修正でき、結果がストリーク・達成率に反映される | P0 |
| FR-10 | リマインド超過ハイライト | 当日ダッシュボードで、リマインド時刻を過ぎた未完了習慣をハイライト表示する | P0 |
| FR-11 | チェックインの一意性保証 | 同一習慣・同一日付のチェックインは重複せず、最新状態を一意に保つ | P0 |

#### 4.1.3 可視化（ストリーク・達成率）

| FR-ID | 機能 | 概要 | 優先度 |
|---|---|---|:--:|
| FR-12 | ストリーク算出 | 習慣ごとに現在ストリーク・最長ストリークを算出する（対象外の日は途切れさせず、対象日の未達成で途切れる） | P0 |
| FR-13 | ストリークの再計算 | チェックイン記録の追加・修正に応じてストリークを正しく再計算する | P0 |

### 4.2 機能詳細と受け入れ基準

各機能の受け入れ基準を定義する。これらは後続のテスト設計工程で検証項目に展開される。中核ロジック
（対象日判定・ストリーク・達成率）の仕様の正本は `functional-design.md`「アルゴリズム設計
（ドメインロジック）」であり、本節はそれと整合させる。

#### FR-01 習慣の登録

- 名前・カテゴリ・繰り返しルール（毎日／週N回／特定曜日）を指定して習慣を登録でき、一覧に反映される。
- リマインド時刻を任意で指定できる。
- 繰り返しルールに応じた付随項目（週N回の N、特定曜日の曜日集合）を指定できる。

#### FR-02 習慣の編集 / FR-03 習慣の削除（アーカイブ）

- 習慣を編集・削除でき、その結果が一覧とチェックイン対象に正しく反映される。
- 削除は物理削除ではなく論理削除（アーカイブ）とし、過去のチェックイン記録を破壊しない。

#### FR-05 リマインド時刻の設定・保持

- 習慣ごとに任意のリマインド時刻を設定・保持できる。
- 第一マイルストーンでは通知の実配信は行わず、時刻の保持のみとする。

#### FR-06 繰り返しルールのバリデーション

繰り返しルールと付随項目の整合を検証し、不正入力をエラーとして拒否する（サーバー側検証）。

| 繰り返しルール | 週N回の N | 特定曜日 |
|---|---|---|
| 毎日（daily） | 指定不可 | 指定不可 |
| 週N回（weekly_count） | 1〜7（必須） | 指定不可 |
| 特定曜日（specific_days） | 指定不可 | 1つ以上選択（必須） |

- 週N回の N が 1〜7 の範囲外、または特定曜日が未選択の場合はエラーとする。

#### FR-07 対象習慣の提示

- 日付を指定すると、その日が繰り返しルール上の対象である習慣のみが提示される。
- 週N回・特定曜日ルールでも正しく判定される（判定仕様は `functional-design.md`「対象日判定」に従う。
  週の起点は月曜始まり／ISO 8601）。

#### FR-08 完了／未完了の記録 / FR-09 過去日の遡り記録・修正

- 各習慣を「完了／未完了」で記録でき、記録は即座に反映・永続化される。
- 過去日を指定して遡り記録・修正ができ、その結果がストリーク・達成率に反映される。
- 繰り返しルール上の非対象日への記録は受け付けない（ビジネスルール上処理不可として拒否する）。

#### FR-10 リマインド超過ハイライト

- 当日ダッシュボードで、リマインド時刻を過ぎた未完了の習慣がハイライト表示される。
- 判定は当日の対象習慣のみを対象に、サーバー時刻基準（リマインド時刻 < 現在時刻）で行う（過去日は対象外）。

#### FR-11 チェックインの一意性保証

- 同一習慣・同一日付のチェックインは重複せず、最新状態が一意に保たれる（記録は upsert 相当）。

#### FR-12 ストリーク算出 / FR-13 ストリークの再計算

- 習慣ごとに現在ストリーク・最長ストリークが算出される。
- 対象外の日は連続を途切れさせず、対象日の未達成で途切れる。
- チェックイン記録の追加・修正に応じてストリークが正しく再計算される。
- 当日が対象日でまだ未記録の場合は「未達成による途切れ」とはみなさない（中立に扱う）。
- 週N回ルールは週（月曜始まり）単位で達成／未達成を判定する。
- 検証すべきエッジケース: 対象外の日を跨いだ継続／対象日の未達成での途切れ／遡り修正による再計算／
  当日未記録の中立扱い。

#### FR-14 達成率の算出

- 週次・月次の達成率＝「期間内の対象日のうち完了した数 ÷ 期間内の対象日の総数」を算出・表示する。
- 期間内に対象日が無い場合は「対象なし」とし、0% とは区別して率を表示しない。
- 週N回ルールは「期間内の対象週数」に対する「達成週数」で率を出す。

#### FR-15 カレンダーヒートマップ / FR-16 ダッシュボード集約表示

- カレンダーヒートマップで、対象日／完了日／未完了日（および未記録日）を視覚的に区別して表示する。
- ダッシュボードに達成率・ストリーク・ヒートマップが集約表示される。

## 5. 非機能要件

非機能要件は独立文書 **`docs/specs/1_requirements/non-functional-requirements.md`（非機能要件定義書）**
を正本とする。同書で NFR-ID（NFR-01〜NFR-14）を採番し、IPA 非機能要求グレードの大分類に沿って
性能・拡張性／信頼性・データ整合性／セキュリティ／運用・保守性・テスト容易性／ユーザビリティを
定義し、各要件に目標・基準と測定方法を付す。

主要な非機能要件の概要は以下のとおり（詳細・測定方法は別紙参照）。

| 分類 | 主な要件 | 代表的な目標 |
|---|---|---|
| 性能・拡張性 | 集計 API 応答／書き込み反映／データ規模 | 集計 API p95 300ms 以内、書き込み反映 200ms 以内（NFR-01, 02, 10, 11） |
| 信頼性・データ整合性 | 永続化／一意性／集計の決定論性 | データ損失なし・一意制約・同一入力で同一結果（NFR-05〜07） |
| セキュリティ | 入力値検証／認証 | サーバー側検証で不正入力を拒否、認証はスコープ外で拡張余地を残す（NFR-08, 09） |
| 運用・保守性・テスト容易性（主眼） | ドメインロジック分離／API 契約一元管理／カバレッジ | 外部依存なしに単体テスト可能、OpenAPI 契約、ドメインロジック 90% 以上（NFR-12〜14） |
| ユーザビリティ | 操作数／視認性 | 3クリック以内でチェックイン、リマインド超過を区別表示（NFR-03, 04） |

> 非機能要件の正本・測定方法・対象外観点の明示は非機能要件定義書に集約する。本節は概要のみを示す。

## 6. スコープ

### 6.1 対象範囲（第一マイルストーン）

- 習慣の管理（登録・編集・アーカイブ・一覧）
- 日次チェックイン（当日／過去日の記録・修正、対象習慣の提示、一意性保証、リマインド超過ハイライト）
- ストリーク・達成率の算出と、ダッシュボード／習慣詳細での可視化（ヒートマップ含む）

### 6.2 スコープ外（後続マイルストーン）

以下は第一マイルストーンでは実装しない。

| 項目 | 内容 | 想定優先度 |
|---|---|:--:|
| リマインド通知の実配信 | リマインド時刻に基づくメール／ブラウザプッシュ等のスケジューリング配信（第一版は時刻の保持のみ） | P2 |
| 認証・マルチユーザー対応 | ユーザー登録・ログインと、ユーザーごとのデータ分離 | P1 |
| 目標連携・AI による習慣提案 | 上位目標との紐付け、達成傾向に基づく習慣提案 | P2 |
| モバイル・オフライン対応 | モバイルアプリ／オフライン利用 | P2 |

## 7. 前提・制約条件

| # | 区分 | 内容 |
|---|---|---|
| 1 | 前提 | 第一マイルストーンは単一ユーザー・ローカル環境前提とする（認証・マルチユーザーなし） |
| 2 | 前提 | 利用端末は PC ブラウザを中心とする |
| 3 | 制約（確定事項） | 日付・時刻はサーバーローカル時刻基準で扱う（ユーザータイムゾーンは持たない） |
| 4 | 制約（確定事項） | 週の起点は月曜始まり（ISO 8601）とする |
| 5 | 制約（確定事項） | リマインド超過判定は、当日の対象習慣のみを対象に、サーバー時刻基準で行う（過去日は対象外） |
| 6 | 制約（確定事項） | 繰り返しルール上の非対象日へのチェックインは受け付けない（ビジネスルール上処理不可として拒否） |
| 7 | 制約 | 習慣の削除は論理削除（アーカイブ）とし、過去のチェックイン記録を破壊しない |

> 上記の確定事項（#3〜#6）の一次情報は `functional-design.md`「データモデル」「アルゴリズム設計」を正本とする。
