# 要件定義工程 成果物作成ガイド

このガイドは、PRD・機能設計書（`docs/baseline/`）をもとに、要件定義工程の顧客提出成果物
（要件定義書・非機能要件定義書）を作成するための実践的な指針を提供します。

> **成果物の配置**: 要件定義書は `docs/specs/1_requirements/requirements-definition.md`、
> 非機能要件定義書は `docs/specs/1_requirements/non-functional-requirements.md`。各スケルトンは
> `SKILL.md`「テンプレートの参照」と `templates/` を参照。本ガイドは中身を書くための手法。

## この2成果物が満たすべき性質

顧客提出物として、以下を満たすことを品質の柱とする。

1. **正本と重複しない** — 数値目標・スコープ・データモデル・アルゴリズムの一次情報は baseline
   （PRD／機能設計書）にある。本成果物はそれを**体系化・詳細化・採番**するのが役割で、同じ事実を
   二重に書かない。baseline の数値は「〜を正本とする」と参照する。
2. **追跡可能（トレーサブル）** — 機能要件に FR-ID、非機能要件に NFR-ID を採番する。以降の工程
   （設計・テスト）はこの ID で要件を参照する。ID は振り直さない（追加は連番）。
3. **測定可能** — 受け入れ基準・非機能目標は「検証できる形」で書く。特に非機能要件は**測定方法**を
   必ず併記する。
4. **抜けを隠さない** — スコープ外・対象外の観点は「なぜ対象外か」を理由付きで明示する。曖昧な
   先送り（「詳細は後で」）を残さない。

## パート1: 要件定義書

### ステップ1: PRD・機能設計書の読み込み

`docs/baseline/product-requirements.md` と `docs/baseline/functional-design.md` を読み、以下を把握する。

- 機能要件（コア機能）、優先度（P0/P1/P2）、受け入れ条件
- スコープ／スコープ外、前提・制約（確定事項）
- データモデル・中核アルゴリズム・API/画面/ユースケース一覧（機能設計書側の正本）

### ステップ2: システム概要・利用シナリオ

- **システム概要**（§2）: プロダクトコンセプト・対象利用者・システム構成の概要を、PRD と整合させて
  簡潔に。構成の正本は architecture.md / functional-design.md を参照する。
- **利用シナリオ**（§3）: 業務プロセスが薄いプロダクトでは、業務フロー図を単独化せず、代表的な
  利用の流れを見出し＋数文で示せば十分。詳細ユースケースは基本設計工程へ引き継ぐ。

### ステップ3: 機能要件の採番（FR-ID）

PRD の機能要件を、**実装・テストの単位**に分解して FR-ID を振る。

- 機能群（例: 管理系 / 記録系 / 可視化系）で小見出しを立て、その中で FR-01, FR-02… と連番。
- 各 FR に「機能名・概要・優先度」を一覧表で示す（§4.1）。
- **粒度の目安**: CRUD を1機能にまとめるか、登録・編集・削除を分けるかはプロジェクト規模で判断する。
  後工程で個別に検証・追跡したい単位に切る。迷ったら分割寄り（追跡しやすい）。

### ステップ4: 機能詳細と受け入れ基準（§4.2）

各 FR に受け入れ基準を書く。これは後続のテスト設計工程で検証項目に展開される。

- PRD の受け入れ条件を踏襲しつつ、**検証可能な粒度**にする。
- 中核ロジック（判定・計算などの仕様）は機能設計書「アルゴリズム設計」を正本として**参照**し、
  ここに再掲しない（重複回避）。
- 入力バリデーション規則は**表**で整理すると明快（区分 × 付随項目の整合表など）。

### ステップ5: 非機能要件節（§5）は別紙参照に

非機能要件の正本は非機能要件定義書（パート2）に置く。要件定義書 §5 は**概要表＋別紙参照リンク**に
留める。これで二重管理を避けつつ、本体だけ読んでも全体像が掴める。

### ステップ6: スコープ・前提・制約（§6, §7）

- **スコープ**（§6）: 対象範囲とスコープ外（後続マイルストーン）を PRD と整合させて明記。
- **前提・制約**（§7）: 特に**確定事項**（日付/タイムゾーン基準・週の起点・各種判定基準など、
  後工程がぶれないよう固めた決定）を表で列挙。一次情報は機能設計書を正本として参照する。
- **残存する未決事項**（§7.1）: 残っていれば列挙、無ければ「なし」と明記（曖昧に濁さない）。

## パート2: 非機能要件定義書

### ステップ1: IPA 非機能要求グレードで分類

非機能要件を以下の大分類で整理する（本プロジェクトに該当するもののみ定義し、限定・対象外は理由を明示）。

- 性能・拡張性 / 信頼性・データ整合性（可用性含む） / セキュリティ /
  運用・保守性・テスト容易性 / ユーザビリティ / 移行性・システム環境

### ステップ2: NFR-ID の採番とサマリー表（§1.3）

PRD の非機能要件・KPI を NFR-ID（NFR-01…）で採番し、サマリー表を作る。以降の工程はこの ID で参照する。

### ステップ3: 各分類の詳細（§3〜§7）— 測定方法を必ず付す

各要件を「要件・目標/基準・**測定方法**」の3列で書く。測定方法は「どのデータ規模・どの環境で・
どう測るか」まで具体化する。数値目標の一次情報は PRD「非機能要件」「成功指標(KPI)」を正本とする。

**良い例**（測定方法まである）:

| NFR-ID | 要件 | 目標・基準 | 測定方法 |
|---|---|---|---|
| NFR-01 | 集計 API 応答時間 | p95 300ms 以内 | 習慣50件・1年分のシードデータでローカル環境で反復呼び出しし p95 を計測 |

**悪い例**（測定不能）:
- 「システムは高速であること」— 数値も測定方法も無い。

### ステップ4: 対象外・限定対応の明示（§8）

スコープに照らして定めない観点（可用性・移行性・システム環境・運用監視・認証など）を、**理由付きで**
表に明示する。「なぜ対象外か」を書くことが顧客提出物としての誠実さになる。後続マイルストーンで
要件化する旨も添える。

### ステップ5: 要件定義書との整合

- NFR-ID は要件定義書 §5 の概要表と一致させる。
- 認証など「セキュリティで触れるがスコープ外」の項目は、§5 で軽く触れ §8 で対象外理由を書く、と
  役割分担する。

## 品質チェックリスト

作成後、以下を確認する。

### 要件定義書
- [ ] すべての機能要件に FR-ID が振られ、一覧表と機能詳細が対応しているか
- [ ] 受け入れ基準が検証可能な粒度か（テスト設計に渡せるか）
- [ ] 中核ロジックを機能設計書から再掲せず参照しているか（二重管理していないか）
- [ ] スコープ外・前提・制約・未決事項が明示されているか（曖昧な先送りがないか）
- [ ] §5 が非機能要件定義書への概要＋参照になっているか

### 非機能要件定義書
- [ ] NFR-ID が採番され、要件定義書 §5 の概要と一致しているか
- [ ] IPA 非機能要求グレードの分類で整理されているか
- [ ] すべての非機能要件に**測定方法**が併記されているか
- [ ] 数値目標が PRD の値と一致しているか（齟齬がないか）
- [ ] 対象外・限定対応の観点が理由付きで明示されているか

## まとめ

要件定義工程 成果物作成の成功のポイント:

1. **baseline を正本として参照**し、二重管理しない
2. **FR/NFR を採番**して後工程から追跡可能にする
3. **受け入れ基準・非機能目標を測定可能に**（非機能は測定方法まで）
4. **スコープ外・対象外を理由付きで明示**（抜けを隠さない）
5. **1ファイルずつ承認**を得て進める（プロジェクト CLAUDE.md のルール）
