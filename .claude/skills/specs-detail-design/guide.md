# 詳細設計工程 成果物作成ガイド

このガイドは、`docs/baseline/functional-design.md`「データモデル」（概念モデル）をもとに、
詳細設計工程の成果物（`docs/specs/3_detail-design/db/table-definition.md`）を作成するための
実践的な指針を提供します。

> **成果物の配置**: スケルトンは `SKILL.md`「テンプレートの参照」と `templates/` を参照。
> 本ガイドは中身を書くための手法。

## この成果物が満たすべき性質

1. **正本と重複しない** — エンティティ名・区分値・ER図・業務ルールは baseline にある。本成果物は
   それを**物理レベルまで具体化**するのが役割で、概念モデルを再定義しない。
2. **論理と物理の対応を明示する** — 概念モデルの camelCase フィールド（例: `recurrenceType`）と
   物理カラムの snake_case（例: `recurrence_type`）の対応が一目でわかるようにする。
3. **必要な時にだけ参照すればよい実装レベル** — カラムの型・NULL可否・デフォルト・物理制約名・
   索引名など、baseline に書くと指標としての見通しを損なう詳細をここに置く。
4. **曖昧な先送りを残さない** — DBバージョン依存、FK削除挙動、`updated_at`の更新方式など、
   この場で決まる粒度の事項は確定させる。

---

## ステップ1: baseline のデータモデルを確認する

`docs/baseline/functional-design.md`「データモデル」の以下を確認する。

- エンティティと区分値（型名と取りうる値）
- ドメイン上の制約（DBでは担保しない、ドメイン層の意味・ルール）
- ER図（論理名でのエンティティ・関係）
- 確定事項（概念レベル）— 日付/TZ基準、削除方針、一意性の単位など

これらは**再掲せず**、物理スキーマ側の記述の前提として参照する。

## ステップ2: テーブルごとにカラム定義表を書く

ER図の各エンティティに対応する物理テーブルを1つずつ起こす。

| カラム（物理名） | 論理名 | 型 | NULL | デフォルト | 説明 |
|---|---|---|:--:|---|---|
| `id` | [論理名] | UUID | 不可 | `gen_random_uuid()` | 主キー |
| `foo_bar` | [論理名] | [型] | 不可/可 | [デフォルト] | [説明・値域] |

**書き方のポイント**:
- 型は実際に使うDB（PostgreSQL等）の型名で書く（`VARCHAR(100)`・`SMALLINT`・`TIMESTAMPTZ`等）。
- 値域・文字数制限など、CHECK制約で表現するものは「説明」列に明記する。
- ER図の論理名（日本語）と物理名（snake_case）の対応が読み取れる見出しにする
  （例: `## habits テーブル（論理名: 習慣）`）。

## ステップ3: 制約・インデックスを書く

物理制約名を付けて列挙する。

| 名前 | 種別 | 内容 |
|---|---|---|
| （主キー） | PK | `id` |
| `foo_status_valid` | CHECK | `status` ∈ { `a`, `b` } |
| `foo_bar_unique` | UNIQUE | (`bar_id`, `date`)。重複防止・upsertの競合ターゲット |
| `idx_foo_date` | INDEX | (`date`)。日付起点の取得用 |

**区分によって必須/任意が切り替わるような整合規則**（例: 種別Aなら項目Xが必須、種別Bなら項目Yが
必須）がある場合は、CHECK制約として物理表現しつつ、**論理的な規則そのものの正本は要件定義書の
該当 FR**に置く（`docs/specs/1_requirements/requirements-definition.md`）。ここでは「この
CHECK制約がその規則を担保している」という対応づけに留め、規則を再定義しない。

## ステップ4: 設計メモ（確定事項）を書く

物理的な実装判断で、後から曖昧にされたくないものを列挙する。

- FK の削除挙動（`ON DELETE CASCADE` / `RESTRICT`）と、対応するエンティティの論理削除方針の関係
- `updated_at` の更新方式（アプリケーション側で明示設定 / DBトリガー）
- DBバージョン依存の関数・型を使う場合はその前提バージョン（例: `gen_random_uuid()` は
  PostgreSQL 13+ 組み込み）
- 索引がどのクエリ（アクセスパターン）のために張られているか

**この場でステータスコード相当の物理判断を確定させる**（「詳細設計で確定」という先送りを残さない
——このファイル自体が詳細設計なので、先送り先がない）。

## ステップ5: 詳細設計への申し送り

物理DDL（マイグレーションSQL）は本ファイルを基に生成する運用ルールを明記する。テーブル・カラムの
追加・変更時は、まず baseline の概念モデル（ER図・区分値）を更新し、本ファイルを追随させる
（正本は baseline の概念モデル、物理詳細は本ファイル）という更新の順序を明記しておくと、後続の
更新者が迷わない。

## 品質チェックリスト

- [ ] baseline の全エンティティに対応する物理テーブルが定義されているか
- [ ] 論理名（camelCase）と物理名（snake_case）の対応が読み取れるか
- [ ] 型・NULL可否・デフォルトがすべてのカラムに明記されているか
- [ ] 制約・インデックスが物理名付きで列挙されているか
- [ ] 区分による必須/任意切り替えがある場合、要件定義書の該当 FR と対応づけているか（規則を
      再定義していないか）
- [ ] 設計メモに曖昧な先送りが残っていないか
- [ ] baseline に書かれているエンティティ名・区分値・業務ルールを再掲していないか

## まとめ

詳細設計工程 成果物作成の成功のポイント:

1. **baseline の概念モデルを正本として参照**し、二重管理しない
2. **論理⇔物理の対応を明示**する（camelCase ↔ snake_case）
3. **物理レベルの詳細に徹する**（型・制約名・索引名・DBバージョン依存事項）
4. **この場で決まることは確定させる**（先送りを残さない）
5. **1ファイルずつ承認**を得て進める
