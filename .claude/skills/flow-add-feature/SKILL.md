# 新機能の追加

このスキルは**2つのモード**を持つ。**起動時の引数の有無で分岐する。**

- **引数なし（企画モード）:** planモードで新機能の**要求を対話的に練り**、
  内容が固まったら `.steering/[日付]-[タイトル]/requirements.md` を作成して**停止する**。
  実装（design.md / tasklist.md 生成・コーディング）には進まない。
- **引数あり（自動実装モード）:** 機能名を起点に、設計 → 実装ループ → 検証 → テスト →
  振り返りまでを、ユーザーの介入なしで**完全に無停止で自動実行する**。
  既に `requirements.md` があればそれを尊重し、再生成しない。

```
[/flow-add-feature]（引数なし） planモードで構想 → requirements.md 作成 → 停止（レビュー）
                                          ↓ ユーザーが内容確認のうえ「続けて」と指示
                          requirements.md を尊重 → design.md / tasklist.md 生成 → 実装 → 検証 → テスト → 振り返り

[/flow-add-feature タイトル]     （requirements.md があれば尊重）上記の実装フローを最初から無停止で実行
```

**分岐の判定:** 起動時に機能名の引数が与えられているか確認する。
- 引数が**ない**（空）→ 下記「モードP: 企画モード」を実行する。
- 引数が**ある** → 下記「モードA: 自動実装モード」を実行する。

---

# モードP: 企画モード（引数なしで起動した場合）

このモードは新機能の**要求を対話的に練り**、内容が固まったら
`.steering/[日付]-[タイトル]/requirements.md` として記録する。
生成した `requirements.md` は、ユーザーがレビューして「続けて」と指示したら、
自動実装モードが**再生成せずに尊重して** design.md / tasklist.md の生成・実装へ進む。

**重要:** このモードは **requirements.md の作成までで停止する**（人間がファイルを目視レビューする
ためのチェックポイント）。ユーザーが続行を指示するまで design.md / tasklist.md の生成や実装には
**進まない**。requirements.md 作成後に、指示なしで実装へ突入してはならない。

## P-ステップ1: 要求を練る（planモード）

### 1-A. まず問いかける（初回レスポンス／ゼロ読込で即返す）

> **重要（レスポンス速度）:** 初回レスポンスは**ファイル読込・`Grep`/`Glob` を一切行わずに**返すこと。
> 起動直後にやることは「テーマを問いかける」ことだけ。`CLAUDE.md` や `docs/` の読込、関連実装の
> 調査は **1-C（テーマ確定後）まで絶対に行わない**。ここで前倒しに調査すると初回応答が大幅に遅くなる。

1. **テーマをヒアリングする（最初に必ず、これだけを行う）**
  - まずユーザーに「どんな機能を考えたいか」を問いかける。
  - 当てがある場合はそれを起点に深掘りする。なければ、（記憶している範囲の）プロジェクトの現状を
    踏まえて候補を軽く提示してよいが、**そのためにファイルを読みに行かない**。
  - ここで一旦ユーザーの応答を待つ。`EnterPlanMode` を含むツール呼び出しもこの応答の後で構わない。

### 1-B. planモードに入る

2. **planモードに入る。** 以降、確定前はファイルを書かず、ユーザーと対話して構想を固める。

### 1-C. テーマ確定後に調査する（初回レスポンス後）

3. **プロジェクト方針の把握**（**1-A でテーマが固まってから**実施。初回レスポンス前には読み込まない）
  - 必要に応じて `CLAUDE.md` および `docs/1_requirements/product-requirements.md` / `docs/2_basic-design/functional-design.md` /
    `docs/2_basic-design/architecture.md` を読み、プロジェクトの北極星と整合する要求か確認する。
  - **確定したテーマに関連する**既存実装のみ `Grep` / `Glob` で軽く調査し、実現可能性の感触を掴む。
    テーマ未確定のまま広く調査しない（的が絞れず無駄打ちになる）。

4. **対話で以下を引き出す**（不明点は仮置きせず、ユーザーに確認する）
  - 機能のタイトル（短く識別できる名前）
  - 背景（なぜ作るのか、どんな課題を解くのか）
  - 実装対象の機能（What。ユーザー体験としてどうなるか／実現したい振る舞い）
  - スコープ（含む / 含まない）
  - 受け入れ条件（検証可能な形で）
  - 成功指標（定量・定性、あれば）
  - 未決事項（実装フェーズで決める点があれば）

5. **要求が固まったら、ユーザーに合意を取る。**
  - 「この内容で requirements.md にまとめてよいか？」を確認し、承認を得てから P-ステップ2へ。

## P-ステップ2: requirements.md の生成

1. **ステアリングディレクトリを決める**
  - 現在の日付を `YYYYMMDD` 形式で取得する。
  - **P-ステップ1の対話で合意したタイトル**を簡潔な名前にし、`.steering/[YYYYMMDD]-[タイトル]/` を決定して作成する。
  - **自動実装モードと同じ命名規約**にすること（自動実装モードが同じディレクトリを再利用できるようにするため）。

2. **requirements.md を作成する**
  - `.claude/skills/flow-steering/templates/requirements.md` のテンプレートに準拠し、
    P-ステップ1で固めた内容を埋めて `.steering/[YYYYMMDD]-[タイトル]/requirements.md` に書き出す。
  - テンプレートの章立て（概要 / 背景 / 実装対象の機能 / 受け入れ条件 / 成功指標 / スコープ外 / 参照ドキュメント）を踏襲する。
  - 未決事項がある場合のみ、末尾に `## 未決事項` セクションを任意で追加し、
    実装フェーズで判断・確認すべき点を箇条書きで残す（自動実装モードの設計フェーズが拾えるようにするため）。

  > ※ ここで作る requirements.md は自動実装モードが**再生成せずそのまま使う**正式な要求書。
  > 「ざっくり」ではなく、受け入れ条件は検証可能な粒度まで詰めること。

3. **ユーザーに報告し、続行を促す**
  ```
  requirements.md を作成しました: .steering/[YYYYMMDD]-[タイトル]/requirements.md
  内容を確認のうえ、続ける場合は「続けて」と指示してください。
  （そのまま design.md / tasklist.md の生成・実装へ進みます）
  ```

4. **ここで停止する。** ユーザーが続行を指示するまで実装に進まない。
  続行の指示（「続けて」等）を受けたら、この requirements.md を尊重したまま
  **モードA の A-ステップ2 以降**を実行して実装まで進める（requirements.md は再生成しない）。

## モードP の完了条件

- `.steering/[日付]-[タイトル]/requirements.md` が作成されている。
- requirements.md が steering テンプレートの章立てに準拠している。
- ディレクトリ名が自動実装モードと同じ命名規約になっている。
- ユーザーに「続けて」での続行を促している。
- design.md / tasklist.md の生成・実装には踏み込んでいない（requirements.md までで停止）。

# モードA: 自動実装モード（機能名を引数で起動した場合）

**重要:** このワークフローは、ユーザーの介入なしに、開始から完了まで完全に自動で実行されるように設計されています。各ステップは完了後、ただちに次のステップへ移行してください。思考の途中でユーザーに確認を求めたり、作業を中断したりしないでください。

**引数:** 機能名 (例: `/flow-add-feature ユーザープロフィール編集`)

## A-ステップ1: 準備とコンテキスト設定

1. 現在のタスクコンテキストを確立する:
  - 機能名: `[引数で与えられた機能名]`
  - 日付: `[現在の日付をYYYYMMDD形式で取得]`
  - ステアリングディレクトリパス: `.steering/[日付]-[機能名]/`
2. **既存の `requirements.md` を確認する（企画モードとの連携）:**
  - `Glob('.steering/*/requirements.md')` で、今回の機能名に対応する `requirements.md` を持つディレクトリが既に存在するか確認する。
  - **存在する場合:** そのディレクトリを新規作成せず再利用し、ステアリングディレクトリパスをそのディレクトリに設定する。この `requirements.md` は企画モードが作成した正式な要求書なので、**削除・上書き・再生成しない**（A-ステップ4で尊重する）。
  - **存在しない場合:** 新規にディレクトリを作成し、`requirements.md` もこのワークフローで生成する。
3. ステアリングディレクトリが未作成なら作成する。
4. 以下の空ファイルを作成する（既に存在する場合はそのまま使う。既存の `requirements.md` は上書きしない）:
  - `[ステアリングディレクトリパス]/requirements.md`（既存がなければ作成）
  - `[ステアリングディレクトリパス]/design.md`
  - `[ステアリングディレクトリパス]/tasklist.md`

## A-ステップ2: プロジェクト理解

1. **`requirements.md` が既にあれば最優先で読み込み、尊重する（企画モード連携）:**
  - ステアリングディレクトリに `requirements.md` が存在する場合、`Read` で読み込み、**正式な要求書**として扱う。
  - これは企画モードでユーザーと合意済みの要求なので、**再生成・上書きしない**。`design.md` / `tasklist.md` 生成の入力としてそのまま使う。
  - `requirements.md` に `## 未決事項` セクションが残っている場合は、設計上の妥当な既定を採用しつつ、判断を振り返り（`retrospective.md`、モード3で作成）に記録する。
2. `CLAUDE.md`を読み、プロジェクトの全体像を把握する。
3. `docs/`ディレクトリ内の永続ドキュメントを確認し、関連する設計思想やアーキテクチャを理解する。

## A-ステップ3: 既存パターンの調査

1. Grepツールを使用し、機能名に関連するキーワードでソースコード(`src/`)を検索する。
  ```bash
  Grep('[機能に関連するキーワード]', 'src/')
  ```
2. 検索結果を分析し、既存の実装パターン、命名規則、コンポーネントの利用方法を特定する。

## A-ステップ4: 計画フェーズ (ステアリングファイルの自動生成)

1. `Skill('flow-steering')`を**計画モード**で実行し、ステアリングファイルの内容を生成する。
  - **`requirements.md` が企画モードにより既に作成済みの場合:** その内容を**再生成せず尊重**し、`design.md` と `tasklist.md` のみを生成する。
  - **`requirements.md` が未作成の場合:** `requirements.md`・`design.md`・`tasklist.md` の3ファイルすべてを生成する。
2. **このステップが正常に完了したら、決して停止せず、ただちにA-ステップ5に進むこと。**

## A-ステップ5: 実装ループ (tasklist.mdの完全消化)

**このステップは、`tasklist.md`の全タスクが `[x]` になるまで自動で繰り返されるループ処理です。**
**このステップが正常に完了したら、決して停止せず、ただちにA-ステップ6に進むこと。**

**ループ開始:**

1. タスクリストの読み込み:
  - `[ステアリングディレクトリパス]/tasklist.md`ファイルを読み込む。

2. 進捗の確認:
  - ファイル内に未完了タスク (`[ ]`) が存在するか確認する。
  - **もし未完了タスクが存在しない場合:** この実装ループは完了とみなし、ただちに**A-ステップ6**へ進む。
  - **もし未完了タスクが存在する場合:** 次の処理（3. タスクの実行）に進む。

3. タスクの実行:
  - `tasklist.md`の**先頭にある未完了タスク**を1つ特定する。
  - そのタスクを完了させるために必要な実装作業を実行する。
  - `Skill('flow-steering')`を**実装モード**で使用する。
  - `Skill('docs-development-guidelines')`のコーディング規約を常に遵守する。

4. タスクリストの更新:
  - 実行したタスクが完了したら、`Edit`ツールを使用して`tasklist.md`を更新し、該当タスクを `[ ]` から `[x]` に変更する。

5. ループ継続:
  - **A-ステップ5の先頭 (1. タスクリストの読み込み) に戻り、処理を繰り返す。**

---
### ※ 実装ループ内の例外処理ルール ※

実装ループの実行中に以下の状況が発生した場合は、このルールに従って自律的に対処し、ループを継続すること。

- **ルールA: タスクが大きすぎる場合**
  - **対処法:** 現在のタスクをより小さな複数のサブタスクに分割する。`Edit`ツールを使い、元のタスクを削除し、その場所に新しいサブタスク（`[ ]`付き）を挿入する。その後、ループを継続する。

- **ルールB: 技術的理由でタスクが不要になった場合**
  - **条件:** 実装方針の変更、アーキテクチャの変更、依存関係の変更など、明確な技術的理由がある場合にのみ適用。
  - **対処法:** `Edit`ツールを使い、該当タスクを `[x] ~~タスク名~~ (理由: [具体的な技術的理由を簡潔に記述])` の形式で更新する。その後、ループを継続する。

- **❌ 絶対禁止の行為:**
  - 未完了タスクを「後でやる」「別タスクにする」などの理由で意図的にスキップすること。
  - 理由なく未完了タスクを放置してループを終了させること。
  - ユーザーに判断を仰ぐこと。

---

## A-ステップ6: 実装検証 (サブエージェント起動)

1. `tasklist.md`の全タスクが完了したことを最終確認する。
2. `Task`ツールを使用し、`implementation-validator`サブエージェントを起動して品質を検証する。
  - `subagent_type`: "implementation-validator"
  - `description`: "Implementation quality validation"
  - `prompt`: "今回実装した `[機能名]` に関する全ての変更点の品質を検証してください。対象ファイルは `[実装したファイルのパスリスト]` です。コーディング規約、エラーハンドリング、テスト可能性、既存パターンとの整合性を重点的に確認してください。"

**このステップが正常に完了したら、決して停止せず、ただちにA-ステップ7に進むこと。**

## A-ステップ7: 自動テストの実行

1. 以下のコマンドを順番に実行し、全てのテストがパスすることを確認する。
  ```bash
  Bash('npm test')
  Bash('npm run lint')
  Bash('npm run typecheck')
  ```
2. いずれかのコマンドでエラーが発生した場合は、問題を分析し、修正コードを生成・適用してから、再度このステップを実行する。

**このステップが正常に完了したら、決して停止せず、ただちにA-ステップ8に進むこと。**

## A-ステップ8: 振り返りとドキュメント更新

1. `Skill('flow-steering')`を**振り返りモード**で実行し、`retrospective.md`（`tasklist.md` とは別ファイル）に申し送り事項を記載する。
  - 実装完了日
  - 計画と実績の差分
  - 学んだこと
  - 次回への改善提案

2. 今回の変更がプロジェクトの基本設計やアーキテクチャに影響を与えるか判断する。

3. 影響がある場合、`docs/`内の関連する永続ドキュメントを`Edit`ツールで更新する。

## モードA の完了条件

このワークフローは、以下の全ての条件を満たした時点で自動的に完了となる。
- A-ステップ5: `tasklist.md`の全てのタスクが完了状態（`[x]`または正当な理由でスキップ）になっている。
- A-ステップ6: `implementation-validator`サブエージェントの検証をパスする。
- A-ステップ7: `test`, `lint`, `typecheck`の全てのコマンドがエラーなく成功する。
- A-ステップ8: `retrospective.md` に申し送り事項が記載されている。

この完了条件を満たすまで、自律的に思考し、問題解決を行い、作業を継続すること。
