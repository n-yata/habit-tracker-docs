# 用語集作成ガイド

## 記法の大原則: テーブル形式で一覧化する

各カテゴリの用語は、見出し（`###`）を並べる形式ではなく、**カテゴリごとに1つのテーブル**へ
まとめる（1用語=1行）。定義項目が繰り返し構造になる用語ほど、テーブルにした方が一覧性・
比較しやすさが高い。

- セル内で改行・箇条書きが必要なら `<br>` と `・` を使う。
- 図・状態遷移図・複数行のコード例など**テーブルに収まらないものだけ**、テーブル直下に補足として置く。
- 例外的に見出し形式を使うのは、フィールド一覧を持つデータモデル用語（エンティティ単位で小テーブルを作る）など、テーブルを入れ子にできないケースのみ。

**悪い例（見出し羅列。項目が縦に伸びて一覧しづらい）**:
```markdown
### タスク (Task)
**定義**: ユーザーが完了すべき作業の単位。
**関連用語**: サブタスク、タスクグループ
**英語表記**: Task

### 優先度 (Priority)
**定義**: ...
```

**良い例（テーブルで一覧）**:
```markdown
| 用語（英語表記） | 定義 | 説明・補足 | 関連用語 |
|---|---|---|---|
| タスク<br>(Task) | ユーザーが完了すべき作業の単位。 | タイトル・説明・期限・ステータスを持つ。 | サブタスク / タスクグループ |
| 優先度<br>(Priority) | タスクの重要度と緊急度を示す指標。 | `high` / `medium` / `low` の3段階。 | タスク |
```

## 基本原則

### 1. 明確で一貫した定義

用語の定義は曖昧さを排除し、誰が読んでも同じ理解ができるようにする。「定義」列は1〜2文で簡潔に、
背景・制約・使用例は「説明・補足」列に書く。

### 2. 具体例を含める

抽象的な定義だけでなく、具体的な使用例や値の一覧を「説明・補足」列に含める。値が複数ある場合は
セル内で `・` 箇条書きにする。

例（繰り返しルールのように取りうる値が複数ある用語）:
```markdown
| 用語 | 定義 | 説明・補足 | 関連用語 |
|---|---|---|---|
| 優先度<br>(Priority) | タスクの重要度・緊急度を示す3段階の指標。 | ・`high`: 緊急かつ重要。即座に対応<br>・`medium`: 重要だが緊急でない。計画的に対応<br>・`low`: 重要度・緊急度とも低い。余裕があれば対応 | タスク / ステータス |
```

### 3. 関連用語をリンクする

用語同士の関係性を「関連用語」列に列挙する（`/` 区切り）。他カテゴリのアルゴリズムや状態を指す場合も
同様に名前で参照する。

## 用語の分類方法

### ドメイン用語

**対象**: プロジェクト固有のビジネス概念。

**テーブル列**: `用語（英語表記） / 定義 / 説明・補足 / 関連用語`

```markdown
## ドメイン用語

| 用語（英語表記） | 定義 | 説明・補足 | 関連用語 |
|---|---|---|---|
| ステアリングファイル<br>(Steering File) | 短期的なタスク管理のために作成する一時的なドキュメント。 | `.steering/[YYYYMMDD]-[task-name]/` に配置し、requirements / design / tasklist / retrospective を含む。作業完了後にアーカイブ。 | 永続ドキュメント / タスクモード |
```

### 技術用語

**対象**: 使用している技術・フレームワーク・ツール。

**テーブル列**: `用語 / 定義 / 本プロジェクトでの用途 / 備考`（備考にバージョン・公式サイト・選定理由などを簡潔に。なければ `—`）

```markdown
## 技術用語

| 用語 | 定義 | 本プロジェクトでの用途 | 備考 |
|---|---|---|---|
| TypeScript | JavaScript に静的型付けを追加した言語。 | 全ソースコードを記述し型安全性を確保する。 | 5.3.x |
| Go | 静的型付けのコンパイル言語。 | backend の実装言語。 | 1.23 以降 |
```

### 略語・頭字語

**原則**: 正式名称を明記し、プロジェクト固有の略語は避ける（一般的な略語のみ）。

**テーブル列**: `略語 / 正式名称 / 意味 / 本プロジェクトでの使用`

```markdown
## 略語・頭字語

| 略語 | 正式名称 | 意味 | 本プロジェクトでの使用 |
|---|---|---|---|
| CLI | Command Line Interface | コマンドラインから操作するインターフェース。 | ツールのメインインターフェース。`src/cli/`。 |
| TDD | Test-Driven Development | テストを先に書いてから実装する開発手法。 | 全ての新機能開発で採用。 |
```

### アーキテクチャ用語

**対象**: システム設計・パターンに関する概念。

**テーブル列**: `用語（英語表記） / 定義 / 本プロジェクトでの適用 / 関連コンポーネント`
メリット・デメリット・依存ルールなど補足が多い場合は「本プロジェクトでの適用」列に要約し、
構造図はテーブル直下にコードブロックで置く。

```markdown
## アーキテクチャ用語

| 用語（英語表記） | 定義 | 本プロジェクトでの適用 | 関連コンポーネント |
|---|---|---|---|
| レイヤードアーキテクチャ (Layered Architecture) | 役割ごとに層を分け、上位から下位への一方向依存に保つ設計。 | UI → Service → Data の3層。下位層は上位層に依存しない。 | UIレイヤー / サービスレイヤー / データレイヤー |

依存方向:

​```
UIレイヤー (cli/) → サービスレイヤー (services/) → データレイヤー (repositories/)
​```
```

## 状態遷移の定義

**対象**: エンティティのステータスや状態。ステータス種別ごとに小テーブルで列挙し、遷移がある場合のみ
Mermaid 図をテーブル直下に添える。

```markdown
### タスクステータス (Task Status)

| ステータス | 意味 | 遷移条件 | 次の状態 |
|----------|------|---------|---------|
| `todo` | 未着手 | タスク作成時の初期状態 | `in_progress` |
| `in_progress` | 進行中 | ユーザーがタスクを開始 | `completed`, `todo` |
| `completed` | 完了 | ユーザーがタスクを完了 | `todo`（再オープン可） |

​```mermaid
stateDiagram-v2
    [*] --> todo: タスク作成
    todo --> in_progress: 作業開始
    in_progress --> completed: 完了
    completed --> [*]: アーカイブ
​```
```

## データモデル用語

**対象**: データベース・データ構造。エンティティ単位で、フィールド一覧をテーブルで示す
（カテゴリ全体を1テーブルにするのではなく、エンティティごとに小テーブルを作る）。

```markdown
### Habit（習慣エンティティ）

習慣を表す永続エンティティ。

| フィールド | 説明 |
|---|---|
| `id` | UUID |
| `name` | 名前（1〜100文字） |
| `archived` | アーカイブ済みか |

**関連エンティティ**: CheckIn ／ **制約**: 繰り返し種別と付随項目の整合
```

## エラー・例外の定義

**対象**: システムで定義されているエラークラス。

**テーブル列**: `エラー / 発生条件 / 対処方法 / 例`
コード例は1行に収まるものはセル内（`` `...` ``）へ。複数行になる場合はテーブル直下に置く。

```markdown
## エラー・例外

| エラー | 発生条件 | 対処方法 | 例 |
|---|---|---|---|
| バリデーションエラー（`ValidationError`） | ユーザー入力がビジネスルールに違反した場合。 | HTTP 400 でフィールド単位の理由を返す。ユーザーは入力を修正。 | `throw new ValidationError('タイトルは必須です', 'title')` |
```

## 計算・アルゴリズムの定義

**対象**: 特定の計算方法・アルゴリズム。

**テーブル列**: `アルゴリズム / 要点／計算式 / 実装箇所`

```markdown
## 計算・アルゴリズム

| アルゴリズム | 要点／計算式 | 実装箇所 |
|---|---|---|
| 達成率算出 | `達成率 = 対象日のうち done の数 / 対象日の総数`<br>例: 対象日 12・done 9 → 75% | `internal/domain/achievement.go` |
```

## 用語の保守・更新

### 用語追加のタイミング

**追加すべき時**:
- 新しい概念が導入された
- チームメンバーから質問があった用語
- ドキュメントで3回以上出現する用語
- 外部サービスやAPIを統合した時

**追加不要な時**:
- プログラミング一般の用語（変数、関数など）
- 一度しか使わない一時的な用語

### 更新のワークフロー

1. **用語の追加・変更**: 適切なカテゴリのテーブルに行を追加し、列を全て埋める。関連用語を参照する。
2. **レビュー**: チームメンバーに共有し、定義の妥当性を確認する。
3. **更新日の反映**: 冒頭の「更新日」を更新する。
4. **影響範囲の確認**: 用語を使用している箇所を検索し、必要に応じてドキュメントを更新する。
