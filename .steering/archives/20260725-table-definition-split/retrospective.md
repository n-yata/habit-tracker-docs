# 振り返り: データモデルの物理スキーマを詳細設計（3_detail-design）へ分離

- 作業日: 2026-07-25
- ブランチ: `docs/20260725-table-definition-split`
- 種別: baseline/specs の役割分担見直し＋スキル新設（学びが多いため retrospective のみ残す）

## やったこと

1. シャビからの指摘（「API一覧・画面一覧は薄いカタログなのに、データモデルだけ物理スキーマまで
   baseline に書いてるのは一貫性がないのでは」）を受け、データモデルの扱いを見直した。
2. `docs/baseline/functional-design.md`「データモデル」を**概念モデル**（エンティティ・区分値・
   ドメイン上の制約・ER図・確定事項）のみに縮小。
3. 物理スキーマ（カラム定義・型・物理制約名・索引名・設計メモ）を
   `docs/specs/3_detail-design/table-definition.md`（詳細設計工程の成果物）へ切り出した。
4. プロジェクト `CLAUDE.md` の「baseline と specs の使い分け」の例外規定
   （データモデルは物理スキーマ含めて baseline、という記述）を修正し、「物理・具体＝詳細設計」の
   原則と整合させた。
5. `specs-detail-design` スキルを新設（`specs-requirements`／`specs-basic-design` と同じ構成）。
6. 作業中に、**同じリポジトリで別セッションが並行して `docs/specs/3_detail-design/` に
   `api/`・`screen/`・`db/` のサブディレクトリ構成で詳細設計を進めていた**ことが判明。自分が
   `3_detail-design/` 直下に置いた `table-definition.md` が、その別セッションの再編により
   `db/table-definition.md` に移動されていた。

## 学び・申し送り

### 1. 「一貫性の指摘」は正本のCLAUDE.mdルールとの矛盾を暴くことがある
- ユーザーからの「API/画面はbaselineが薄いのに、DBだけ物理まで書いてるのはおかしくないか」という
  指摘がきっかけで、CLAUDE.md自体の中に**自己矛盾**（「データモデル（物理スキーマ含む）はbaseline」
  という明示例外と、「物理・具体＝詳細設計」という一般原則が食い違っていた）を発見した。
- 申し送り: ルールを機械的に踏襲するだけでなく、「他の同種の分割判断と一貫しているか」を都度
  問い直す。プロジェクトのCLAUDE.md自体が古い判断を引きずっていることがある。

### 2. リンク切れを起こさず移動するには、参照元を全部洗ってから動かす
- 物理スキーマを移動する前に `grep -rl` で「設計メモ（確定事項）」「テーブル定義（物理スキーマ）」
  「物理制約名（habits_recurrence_type_valid 等）」を全文検索し、参照している全ファイル
  （baseline 本体・screen-design.md・スキルテンプレート・CLAUDE.md）を洗い出してから移動した。
  screen-design.md が「baselineデータモデルの整合表」を参照していた箇所を見落とさず修正できたのは
  この事前調査のおかげ。
- 申し送り: 正本を移動・分割するときは、必ず移動前に全文検索で参照元を洗う。「その場で気づいた
  ものだけ直す」ではリンク切れが残る。

### 3. 並行セッションによる同一ディレクトリの競合編集に気づいたら、必ず止めて確認する
- 作業中に `docs/specs/3_detail-design/` 配下へ、自分が作った覚えのない `api/`・`screen/` 配下の
  ファイル群（別セッションによる詳細設計）が出現していることに気づいた。さらに、自分が
  `3_detail-design/` 直下に書いた `table-definition.md` が、その別セッションの `db/`
  サブディレクトリ再編に巻き込まれて移動されていた（内容は無事）。
- CLAUDE.mdの「自分の作業範囲外の未コミット変更を見つけたら、コミットに巻き込まず、ユーザーに
  確認する」ルール通り、気づいた時点で一度作業を止めてユーザーに報告した。
- ユーザーの「コミットして」という指示を受けたが、それでも**自分が書いた参照リンクが実際のファイル
  位置とズレている**ことは看過せず、コミット前にリンクを実際のパス（`db/table-definition.md`）に
  修正してからコミットした。「進めていいと言われた」ことと「壊れた状態のまま進めていい」は別。
- 申し送り: 複数セッション・複数エージェントが同じリポジトリの同じ領域を触る運用では、
  コミット直前に必ず `git status` で無関係な変更が混入していないか確認し、混入があれば
  コミット対象から明示的に除外する（`git add` は個別ファイル指定で行い、`git add -A` を安易に
  使わない）。

## 次への注意
- `docs/specs/3_detail-design/` の `api/`・`screen/` 配下（他セッションの成果物）は、
  今回のコミットに含めていない。次にこのブランチ・このディレクトリに触るときは、まず
  `git status` で現在の全体像を確認し、他セッションの作業が正式にコミットされているか、
  まだ未コミットのままかを確認してから進める。
- `specs-detail-design` スキルの出力先は `docs/specs/3_detail-design/db/table-definition.md`
  （`db/` サブディレクトリあり）に更新済み。今後このスキルを使う際は、この構成
  （`db/`・`api/`・`screen/` 等の対象別サブディレクトリ）を前提にする。
