## 学び・申し送り

### 1. specs/ は「顧客提出成果物」、baseline は「指標＝正本」という役割分担
- `docs/baseline/` は指標かつ正本。`docs/specs/N_*/` は各工程で顧客レビュー・承認を受ける
  **提出成果物**。specs は baseline を正本として**体系化・詳細化・ID採番**するのが役割で、
  数値・スコープ・データモデル等は baseline を正本として参照し**二重管理しない**。
- 非機能要件のように分量が出るものは独立文書に切り出し、本体（要件定義書）側は概要＋別紙参照に
  留めると、正本の一本化と本体の可読性を両立できる。

### 2. 「作るべきか」をまず問う — RTM を見送った判断
- 要件トレーサビリティマトリクス（RTM）は当初 1_requirements の候補に挙げたが、
  **設計側の対応（FR↔画面/API/UC）は既に `functional-design.md` のモジュール構成図・画面設計・
  ユースケース一覧で表現済み**であり、テスト側の列は後続のテスト設計工程まで埋まらない。
  「半分再掲・半分空欄」になるため、規模（FR16個・単一ユーザー）に対して費用対効果が低いと判断し
  見送った。
- 申し送り: 新規ドキュメントを足す前に「その情報は既存ドキュメントで表現済みでないか」「今の工程で
  埋まるのか」を先に確認する。埋まらない列を持つ追跡表は陳腐化しやすい。

### 3. 非機能要件は IPA 非機能要求グレード＋測定方法＋対象外明示で質が上がる
- 大分類（性能・拡張性／信頼性／セキュリティ／運用保守・テスト容易性／ユーザビリティ／移行性・
  システム環境）で章立てし、各要件に**測定方法**を併記、スコープ外観点は**理由付きで明示**する
  （可用性・移行性・認証など）。これが顧客提出物としての誠実さと検証可能性になる。

### 4. スキルのプレフィックスは「箱」を表す — docs-* は曖昧だった
- `docs-*` は baseline 成果物と specs 成果物の両方に付いていて、どの箱を作るスキルか判別できなかった。
  ディレクトリ名に合わせ `baseline-*`（`docs/baseline/`）/ `specs-*`（`docs/specs/`）に分離。
- 申し送り: スキルのプレフィックスは出力先ディレクトリと対応させると、増えても迷子にならない。
  リネーム時は `.claude/README.md`・`.claude/settings.local.json` の `Skill(...)` 許可・
  各 SKILL.md の相互参照・`flow-*` からの参照を漏れなく追従させる（CLAUDE.md「.claude カタログの維持」）。

### 5. 技術的ハマり — Windows で `sed -i` を使うと EOL がノイズになる
- `sed -i` は CRLF ファイルを LF で書き戻すため、**置換が発生していないファイルまで**
  `git status` 上は M に見える。ただし `core.autocrlf` が効いていればステージ時に正規化され、
  `git diff --cached --stat` には**実内容の変更だけ**が残る（EOL-only 差分は消える）。
  コミット前に `git diff --cached --stat` で実変更を確認すれば安全。
- `git mv` は**未追跡（untracked）ディレクトリには使えない**（"source directory is empty" エラー）。
  新規作成直後でまだ add していないディレクトリは通常の `mv` でリネームする。
- 機械的な一括リネームは sed が実務的だが、EOL 影響を理解した上で、最後に
  `git diff --cached` で内容差分を必ず目視確認すること。
