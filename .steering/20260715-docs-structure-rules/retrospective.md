## 学んだこと

**設計・ドキュメント体系の学び**:
- ドキュメント配置は「工程で分類」が第一原則。**基本設計＝論理/外部設計、詳細設計＝物理/具体（実ファイル・ツリー）**。`functional-design`＝基本、`repository-structure`＝詳細が典型。
- 「〜のような気もする」という配置の違和感の多くは、配置ミスではなく**端の内容が複数ドキュメントに重複している**ことが原因。対処はファイル移動ではなく**正本の一元化＋参照リンク化**。
- `domain-logic` のようなアルゴリズム設計は基本↔詳細の境目だが、「設計仕様の高度」に留め、実装判断は `.steering/`・実装リポジトリへ委譲すれば基本設計に収まる。
- これらの判断基準を CLAUDE.md に恒久ルール化したので、今後は同じ問答を繰り返さない。

**プロセス上の注意（重要な申し送り）**:
- 作業中、ユーザーが IDE 側で並行して別作業（commands→skills 移行）を進めており、私の**未コミットのドキュメント編集群が先行コミット `54ab489`「commands を廃止し skills に統合」に巻き込まれて一緒にコミットされていた**。結果、ドキュメント整理の変更がコミットメッセージに現れず、履歴上の追跡性が下がった。
- 検知の仕方: コミット前に `git status` が想定より少ないファイルしか出さなかったことから、`git log` / `git show HEAD:<file>` で「自分の変更が既にHEADに入っている」ことを確認して判明。

## 次回への改善提案
- 中規模以上のドキュメント整理でも、着手時に軽量ステアリング（または Todo）で全体像を先に描くと、作業の途中拡大（今回の軽微→再編への発散）を検知しやすい。
- テンプレート（`.claude/skills/` 配下）と実ドキュメント（`docs/` 配下）は乖離しやすい。機能設計を分割・改名したら**同じコミットでテンプレート側も追従**する運用を徹底する。
- **並行編集環境では、コミット前に必ず `git status` で自分の変更範囲を確認**し、他者の変更（`settings.local.json` 等）を巻き込まない。区切りごとに小さくコミットして追跡性を保つ。
